## Findings

Analysis scope: sampled stories 9.3, 9.6, 9.9, 9.10, 9.11 for spec-to-implementation reconciliation (highest
cross-story/data-integrity risk per `epic-9-context.md`); 9.1, 9.2, 9.4, 9.5, 9.7, 9.8, 9.12 were not individually
reconciled line-by-line. Diff-scope review (adversarial/edge-case/verification-gap) was done inline over the
top-churn files and the two flagged cross-story boundaries (9.3↔9.11, 9.9↔9.10) — the `bmad-review` skill was not
invocable from the analysis subagent's context, so this is narrower than a full 99-file diff-scope pass.

### Duplication map

- **[notable] Confirm-dialog pattern reimplemented a third time instead of consolidated.**
  `bp_front/src/components/DeleteFeedbackDialog.tsx` (new, 110 lines) reimplements the same
  open/prevOpen/shown-entry state machine and loading/error/confirm/cancel handling already present in
  `bp_front/src/components/DeleteUserDialog.tsx` (110 lines, pre-epic) — its own comment says it's "modeled on
  DeleteUserDialog.tsx." Both duplicate what the pre-existing generic `ConfirmDialog.tsx` (111 lines, from Story
  5.5) already provides (`title`/`description`/`confirmLabel`/`confirmColor`/`onConfirm`/`onClose`, its own
  loading+error state, re-entry guard). `DeleteUserDialog.tsx` predates Epic 9, so the pattern drift already
  existed, but Epic 9 had the opportunity to consolidate onto `ConfirmDialog` for the new admin-feedback-deletion
  dialog and instead copied the divergent pattern again.
  **Failure scenario**: a future UX or accessibility fix to the confirm-dialog flow (e.g. focus handling, a
  loading-state tweak) applied to `ConfirmDialog` silently does not reach `DeleteUserDialog.tsx` or
  `DeleteFeedbackDialog.tsx` — three copies now drift independently.
  **Source**: `bp_front/src/components/DeleteFeedbackDialog.tsx` (whole file) vs.
  `bp_front/src/components/ConfirmDialog.tsx`, `bp_front/src/components/DeleteUserDialog.tsx`.
  **Disposition**: defer — not blocking, but flagged so a later cleanup story consolidates all three onto
  `ConfirmDialog` rather than the count growing to four next epic. **Prevents-the-next-one**: none of the 12
  stories' specs mention checking for an existing generic component before adding a new confirm dialog; add "reuse
  `ConfirmDialog` for any new destructive-confirm flow" as an explicit constraint the next admin/destructive-action
  story's spec states, rather than relying on the implementer to notice the existing pattern.

### God-class / size growth

- **[minor] `ItemLifecycleTest.kt` is 1671 lines / 44 flat `test(...)` blocks, no nested `context` grouping.**
  Legitimately covers item create/edit/check/scheduler/multi-store/category-cascade interactions — this
  cross-cutting scope is inherent to the epic (several stories touch the same item lifecycle), not a mistake — but
  the file had zero internal structure before this epic's +803 lines and still has none after. **Failure
  scenario**: not a correctness defect; a maintainability one — the next story that needs to add or find an
  item-lifecycle test case has no `context` boundary to orient by. **Source**:
  `bp_back/src/test/kotlin/com/bagplease/ItemLifecycleTest.kt` (1671 lines total,
  git_evidence.py: +803/-28 this epic). **Disposition**: defer — split by concern (lifecycle / multi-store /
  category-guard) in a future test-hygiene pass, not urgent enough to block this epic's acceptance.
- `ListShoppingPage.tsx` (634 lines, +149/-22 from the FAB) and `AdminPage.tsx` (510 lines, +308/-56 from
  pagination) both grew substantially but are route-level container components with no obvious extractable
  sub-component left inline — read as legitimately large, not god-classes. **Accept as-is.**
- `ItemService.kt` (232 lines) stayed well-organized with named private helpers despite the multi-store change
  touching it — **accept as-is / win**.

### Spec-to-implementation reconciliation

- **Win — 9.3↔9.11 cross-story guard is real, not just claimed.** `epic-9-context.md` calls out that 9.3's
  category-delete cascade must land before/with 9.11's shopping FAB because "its category validation on item save
  is what stops the FAB creating items in a just-deleted category." Verified: `requireCategoryOnList` in
  `bp_back/src/main/kotlin/com/bagplease/entity/item/ItemService.kt` is one private function called from both the
  create (`:53`) and update (`:90`) branches of `saveItem`, and from the checked-status path (`:131`) — genuine
  shared enforcement, not a reimplementation. `spec-9-11-an-item-can-be-added-from-the-shopping-screen.md:57,66`
  correctly documents this as an existing dependency rather than re-deriving it.
- **Win — 9.6 multi-store migration matches spec exactly and closes a real prior bug.** `Migration.kt` keeps the
  epic-4 and epic-9 migrations as independent suspend functions each keyed on its own `app_migrations` record —
  the file's own comment documents that this fixes a pre-9.6 bug where an early return in migration N would skip
  migration N+1 forever. `StoreNames.normalize` (`bp_back/.../item/StoreNames.kt`) does trim + drop-blank +
  case-insensitive-dedupe-keep-first-occurrence exactly as specced, explicitly using `Locale.ROOT` to avoid the
  Turkish-İ casing bug, with a documented frontend mirror in `storeValue.ts`. The completion record is written
  last, so an interrupted migration re-runs safely. This was the epic's highest-risk, one-shot/non-repeatable
  change and it held up under adversarial reading — no integrity defect found.
- **Win — 9.9/9.10 feedback slice matches the "no cache, no reactive stream, no subscription" constraint.**
  `FeedbackService.kt` is 48 lines with no `Flow`/cache. The spec's claim that the two duplicated `requireAdmin()`
  checks were consolidated into one shared helper is real: `requireAdmin()` is defined once in
  `plugins/GraphQLAuth.kt` and reused by `FeedbackApi.kt`, `UserAdminApi.kt`, and `ApplicationConfigApi.kt`
  (verified by grep across all three call sites).
- No dropped requirements or unspecified added behavior found in the five stories sampled (9.3, 9.6, 9.9, 9.10,
  9.11). 9.1, 9.2, 9.4, 9.5, 9.7, 9.8, 9.12 were not individually reconciled — narrowed scope, not "checked and
  clean."

5. **[carry-forward, escalated, still open] F21 — fix `git_evidence.py`'s story-id matcher.** It expects ids
   spelled with a dash (`9-1`, the form `detect-epic` returns) but this project's commit-subject convention spells
   them with a dot (`Story 9.1: ...`), so the matcher silently returns `"stories": []` for every commit unless the
   caller manually reformats the ids first (as this run did). This has now bitten two epics in a row (Epic 8: 0/16
   matched; Epic 9: 0/12 matched until manually worked around). Owner: tooling (md). Concrete fix options: normalize

   `--story-id-format` flag, or match on the numeric epic.story pair regardless of separator
   (`r"\b9[.\-]1\b"`-style). This is a retrospective-tooling defect, not an epic-9 code defect — it affects every
   future retro run, especially headless ones with no human to notice the empty attribution.
