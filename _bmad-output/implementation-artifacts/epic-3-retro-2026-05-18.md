## What Went Well

### Short, focused scope executed cleanly

Epic 3 was defined entirely in the Epic 2 retrospective with clear, bounded stories. No scope creep. Execution matched
the plan.

### Route guard and dialog error fix were surgical

Story 3.1 transferred the `admin/layout.tsx` pattern to `register/layout.tsx` without guesswork. Dialog error
propagation was a targeted fix — `ConfirmDialog` already had the error display infrastructure; only the handlers needed
to throw on `result.error`.

### Unhappy-path checklist now structural

The checklist embedded in `bmad-create-story/template.md` appears in every future story automatically. Both 3.1 and 3.2
used it. This is the most durable process improvement from the last two epics.

### E2E coverage now covers all Epic 2 admin flows

Story 3.2 delivered 8 new tests covering create/delete/reset user, registration toggle, login screen adaptation, admin
guard redirect, and nav menu visibility. All 16 tests (8 new + 8 existing) pass. `webServer` config means
`npm run test:e2e` no longer requires manual stack startup.

### TOCTOU regression test added

The MongoDB unique index behavior under concurrent registration is now covered. Test passes and has regression value
even if the Ktor test engine doesn't guarantee true simultaneity.

### Deferred-work triage generated focused scope

The Epic 2 retro's triage action item was completed — it directly produced Story 3.1's scope. High-value items
addressed; remainder re-deferred with clear categorization.

## What Didn't Go Well

### Gradle MCP evaluation not completed (again)

Winston's Epic 2 action item to evaluate the Gradle MCP server was not completed. The `../gradlew` footgun remains.
Carried forward to Epic 4 with explicit blocker status.

### `ConfirmDialog` Cancel button violates AC5

`ConfirmDialog.tsx:65` disables Cancel while a mutation is in-flight. AC5 of Story 3.1 requires Cancel to remain
interactive at all times. The dev agent documented it as a review decision ("no changes to ConfirmDialog.tsx") rather
than fixing it. The fix is a one-line change — `disabled={loading}` removed from the Cancel button. Folded into Epic 4
Story 4.1.

### `webServer` config has CI reliability gaps

Three deferred items from Story 3.2's review:

- No teardown command — containers accumulate on CI across runs
- Health check only pings nginx, not Ktor/Next.js — early tests may hit 502s during backend warmup
- No stdout/stderr filtering — compose startup failure silently waits the full 120s timeout

Flaky E2E tests are worse than no E2E tests. This needs to be addressed before E2E becomes load-bearing in CI.

### TOCTOU test may not prove true concurrency

Ktor `testApplication` may serialize coroutines on a single-threaded engine. The test verifies the MongoDB unique index
catches duplicates but may not exercise a true simultaneous race. The index is the real protection regardless.

## Key Insights

1. **Short focused epics work when scope is defined upfront.** Epic 3 was defined entirely in the Epic 2 retro. Zero
   ambiguity going in meant clean execution coming out.

2. **Structural process changes outlast individual action items.** The unhappy-path checklist in the story template is
   more durable than any single action item — it enforces the behavior automatically on every future story.

3. **Action items need named owners and explicit verification at the next retro.** The Gradle MCP slipped twice. Moving
   it to Epic 4 prep as a blocker (not just an action item) applies the right pressure.

4. **E2E infrastructure is only valuable if it's reliable.** The `webServer` gaps are a risk that compounds over time —
   fix them before CI depends on E2E tests passing.

5. **Review decisions need a home.** The Cancel button issue was caught in review, documented as a decision, and then
   fell out of sight. Decisions that defer a known bug need to land in deferred-work.md explicitly.

## Epic 4 Preparation

### Epic 4 Defined: Personal Lists & Sharing

Outcome of this retrospective.

**Product decisions (recorded):**

- Each user can create and own multiple lists
- Sharing grants full write access — collaborators are peers of the owner, no role distinction
- Existing global list migrates to admin user on first deploy after Epic 4
- Subscriptions must be scoped per-list (current global `MutableSharedFlow` broadcast won't work)
- UX requires a list navigation/selection layer — significant frontend redesign

**Architecture implications (Winston):**

- New `List` entity across all layers: Storage → Mongo → GQL → Service
- `ListMember` join concept (userId + listId) for sharing
- Per-list subscription scoping: per-list `SharedFlow` or filtered broadcast
- Data migration: seed admin's list from existing items/categories on first startup
