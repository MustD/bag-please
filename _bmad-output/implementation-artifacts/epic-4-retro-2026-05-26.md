## What Went Well

### Architecture held under the largest epic yet

Eight stories layered cleanly on top of each other. The `verifyMembership`-first pattern, Arrow `raise` error handling,
and per-list SharedFlow subscription scoping were architecturally sound. No story had to break a contract established by
a prior story.

### Backend test growth was organic and meaningful

21 tests after 4.1, 105 by the end of 4.4 — each story added targeted coverage for its domain. Per-list isolation
tests (cross-tenant subscription verification) and scheduler seeding patterns (direct MongoDB BSON date injection) were
non-trivial and were written correctly.

### BPSheet spike approach paid off

Story 4.6 validated the `SwipeableDrawer`-based approach definitively before stories 4.7 and 4.8 built on it. The spike
decision prevented a potential mid-epic pivot to a custom implementation.

### Code review was load-bearing

Every story had meaningful review findings that caught real bugs: `TAB_MAP` prefix collision (4.5), `removingIds` never
cleaned up (4.7), `renameList` missing admin block guard (4.8), `rejectInvite` allowing ACCEPTED→DECLINED demotion (
4.3). The review process is working.

### All PRD requirements shipped

FR34 through FR56 — every requirement defined in the epic was implemented. From a specification-completeness
perspective, Epic 4 is fully delivered.

## What Didn't Go Well

### App is not in a usable state

md could not complete a manual smoke test. Mobile login fails on a real device. The app behavior was strange enough that
diagnosis requires actually running it. We shipped 8 stories and left the product in an unverifiable state.

### Zero E2E tests on four significant UI stories

Epic 3's retrospective established a team agreement: "E2E stories planned inside every epic with significant UI
stories." Epic 4 had four frontend stories (4.5, 4.6, 4.7, 4.8) and zero E2E coverage. The agreement was violated
entirely.

### 'TypeScript clean' was accepted as 'works'

The definition of done relied on: TypeScript compiles, backend tests pass, component rendered. Nobody ran the full app
with all layers connected and verified a user journey end-to-end. Component-level correctness does not compose
automatically into feature-level correctness.

### Two scope gaps discovered mid-epic

`renameList` mutation and `uncheckedItemCount` field were both missing from the backend until Story 4.8 discovered the
need during implementation. They were added without a separate story. This worked, but the pattern is fragile — scope
discovered mid-implementation is scope that wasn't reviewed upfront.

### Gradle MCP evaluation slipped for the third time

Winston's action item to evaluate the Gradle MCP server was open after Epic 2 and Epic 3 retros. It slipped again. Three
slips indicates it needs to be a formal story blocker, not an action item.

## Key Insights

1. **'Done' means the user can use it, not that TypeScript compiles.** Feature correctness requires a running app with
   real users, not just passing type checks and unit tests.

2. **E2E stories are not optional on UI-heavy epics.** A team agreement that isn't structurally enforced will be missed.
   Enforcement point: a story cannot be 'done' without E2E coverage for its critical user-facing path.

3. **The larger the epic, the more deferred work accumulates.** Eight stories of deferred items is too much to address
   inline. A triage story at the start of Epic 5 is required — same pattern as Story 3.1.

4. **Mobile verification belongs in Definition of Done.** The app is mobile-first by design. Real-device testing of at
   minimum the auth flow should be required before any frontend story is marked done.

5. **Scope gaps need a home.** Discoveries mid-story (renameList, uncheckedItemCount) worked out this time.
   Systematically, they should generate a note in the story and be confirmed with the architect before implementation,
   not silently added.

## Team Agreements (updated)

- **E2E tests are UI tests.** API calls permitted only for environment preparation (seeding users, resetting
  collections). No API-only test paths.
- **Every E2E test maps to one or more FRs.** Test file or `describe` block includes the FR number(s).
- **A story is not 'done' until E2E coverage exists for its critical user-facing path.** (New — replaces the prior
  softer agreement.)
- **E2E stories planned inside every epic with significant UI stories.** (Continuing from Epic 3 — now with harder
  enforcement via the above.)
- **Unhappy-path checklist in every story.** (Continuing from Epic 2.)
- **Previous retro action items reviewed at the start of every retro before new items are added.** (Continuing from Epic
  3.)
