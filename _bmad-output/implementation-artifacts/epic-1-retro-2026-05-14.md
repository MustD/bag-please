## What Didn't Go Well

### Concurrency not reasoned about during design

Two independent concurrency bugs were caught by review, not by design:

- **Story 1.1:** TOCTOU race between duplicate-username check and save in `UserService`
- **Story 1.3:** Concurrent 401 refresh race — two simultaneous GraphQL errors both calling `authApi.refresh()`, causing
  cookie rotation and silent logout

Both were patched, but neither has a regression test verifying the fix holds. The root cause: concurrency scenarios were
not explicitly reasoned about during implementation.

### Systematic gap in unhappy-path handling

Unguarded error cases surfaced in five of six stories:

- `parseJwt` throws on malformed input (1.3)
- `observer.complete()` called instead of `observer.error()` on refresh failure (1.3)
- Non-JSON error responses swallowed in `changePassword` (1.5)
- `authApi.register` success response JSON parse unguarded (1.4)
- Missing `Suspense` fallback props causing blank screens (1.4)

This is a systematic implementation gap, not individual mistakes.

---

## Key Insights

1. **Review is catching what design should prevent.** The process is healthy but we're spending review cycles on things
   a design checklist could eliminate earlier — especially for concurrency and error paths.
2. **The `UserStorage` layer added complexity without payoff.** Login is a once-per-30-days operation; the in-memory
   cache's hot-path justification doesn't hold. The TOCTOU race from 1.1 was a direct consequence of trying to enforce
   uniqueness in a `ConcurrentHashMap`.
3. **Admin operations belong in GraphQL.** The existing Apollo Client + auth header infrastructure means admin CRUD gets
   type safety, caching, and codegen for free. Only auth endpoints (cookie mechanics) must stay REST.

---

## Architectural Decisions Made in Retrospective

### Decision 1: Remove UserStorage — UserService goes direct to MongoDB

**Rationale:** Login is ~once per 30 days per user (refresh path never touches user storage). In-memory cache adds the
dual-map pattern, `@Volatile` synced flag, and TOCTOU risks for zero observable benefit. MongoDB unique index on
`username` is the correct place for duplicate prevention.
**Impact:** Story 2.0 added as first Epic 2 story to execute this simplification before any new feature work.

### Decision 2: Admin operations via GraphQL, auth via REST

**Rationale:** `users` query, `createUser`/`deleteUser`/`resetUserPassword` mutations, `applicationConfig` query, and
`setRegistrationEnabled` mutation all fit cleanly in GraphQL — no cookie mechanics involved. Auth endpoints stay REST (
httpOnly cookie `Set-Cookie` is not compatible with Apollo Client's response handling).
**Impact:** Story 2.2 ACs rewritten to GraphQL. AR2 updated in epics.md.

### Decision 3: ApplicationConfig direct to MongoDB, no in-memory cache

**Rationale:** Registration toggle is an infrequent admin operation. An in-memory cache adds invalidation complexity for
no practical benefit at this scale.
**Impact:** AR4 and NFR12 updated. Story 2.1 ACs simplified.
